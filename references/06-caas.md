# CaaS — Charging as a Service

CaaS charges money from an end user's mobile account — prepaid balance is reduced, postpaid is
added to the monthly bill. No cards, no wallet, no cash.

**This API moves real money belonging to real people.** Every rule in this file exists because
breaking it costs someone money.

| Service | Endpoint | Direction |
|---|---|---|
| **OTP Generation** (direct debit) | `POST /caas/direct/debit` | You call it |
| **OTP Verification** | `POST /caas/otp/verify` | You call it |
| **Charging Notification** | Your Charging Notification URL | The platform calls you |

---

## The most important thing on this page: a charge is three exchanges

mSpace charging is **OTP-authorised**. There is no single call that takes money.

```
1. POST /caas/direct/debit          you        → mSpace generates and SMSes an OTP to the subscriber
     ← statusCode P1003, requestCorrelator, internalTrxId
                                                 NOTHING HAS BEEN CHARGED YET

2. subscriber reads the OTP and enters it in your application

3. POST /caas/otp/verify            you        → the one-time charge is deducted
     ← statusCode S1000, status true

4. POST <your Charging Notification URL>        ← the platform settles the transaction
     statusCode S1000, TotalAmount, paidAmount, balanceDue
```

Two consequences that break naive code:

- **The success code for step 1 is `P1003`, not `S1000`.** A client that only accepts `S1000`
  reports every successful charge request as a failure — and, if it retries, generates a second
  OTP for a subscriber who is halfway through the first.
- **`referenceNo` in step 3 is the `requestCorrelator` from step 1**, not your `externalTrxId`
  and not an OTP-API `referenceNo`. Getting it wrong gives you `E1855`.

---

## The five charging rules

1. **The amount must be pre-agreed and disclosed to the subscriber before they subscribe.**
   Charging amount and frequency are provisioning-level settings on the application, for prepaid
   and postpaid separately.
2. **`externalTrxId` is your idempotency key.** Generate it once, persist it *before* the HTTP
   call, and reuse the same value for any retry of that same logical charge. Its documented
   purpose is exactly this: to map the request to the response, and to answer inquiries about a
   transaction.
3. **Never retry a charge with a fresh `externalTrxId`.** A timeout does not mean the charge did
   not happen. Reconcile against the charging notification — never re-roll the id.
4. **Never charge from a request you did not authenticate.** A webhook body, an MO SMS, or a
   USSD keypress is not authorisation on its own.
5. **A charge must be traceable to a user action.** Log who, what, when, how much, which
   `externalTrxId`, which `internalTrxId`, and what the subscriber saw before they agreed.

## Step 1 — OTP Generation (direct debit)

```
POST /caas/direct/debit
Content-Type: application/json;charset=utf-8
```

This service initiates a one-time charge on the subscriber's mobile account. On the request,
mSpace generates and sends an OTP to the subscriber's MSISDN, which the subscriber must enter
into your mobile or web application to authorise the one-time charge.

### Request

```json
{
  "applicationId": "APP_000999",
  "password": "…",
  "externalTrxId": "256091232",
  "subscriberId": "tel:94702725777",
  "paymentInstrumentName": "Mobile Account",
  "amount": "5.00",
  "currency": "LKR"
}
```

| Parameter | Description | Type | M/O |
|---|---|---|---|
| `applicationId` | Application ID from provisioning. Single value per request. | String | **M** |
| `password` | The API key sent to your registered email address on the platform upon application approval. | String | **M** |
| `externalTrxId` | **Your** transaction ID, generated by the application to map the request with the response. Needed to answer inquiries about a transaction. Single value per request. | String | **M** |
| `subscriberId` | MSISDN of the subscriber to be charged, `tel:` prefixed. May be a masked number. Single value per request. | String | **M** |
| `paymentInstrumentName` | The name of the payment instrument. Value: `Mobile Account`. Single value per request. | String | **M** |
| `amount` | Amount to be reserved for charging, sent as a **string**. Single value per request. | String | **M** |
| `currency` | Currency unit of the amount. **Only `LKR` is allowed.** Single value per request. | String | **M** |
| `applicationHash` | A unique hash generated by your application to ensure request integrity and authenticity, using a mutually agreed hashing algorithm (for example SHA-256) over agreed request parameters. Single value per request. | String | O |

### Response

```json
{
  "timeStamp": "2026-11-08T08:02:16.913Z",
  "externalTrxId": "256091232",
  "statusDetail": "Successfully sent OTP to user.",
  "requestCorrelator": "8801442233146169943053700500040",
  "internalTrxId": "9110808020001876",
  "statusCode": "P1003"
}
```

| Parameter | Description | M/O |
|---|---|---|
| `statusCode` | `P1003` — **the success code for this call.** The OTP was sent; nothing is charged yet. | M |
| `externalTrxId` | Echo of your ID — **assert it matches what you sent** | M |
| `requestCorrelator` | The unique identifier the system uses internally to identify the transaction. **Pass this as `referenceNo` to OTP Verification.** | M |
| `internalTrxId` | The transaction ID generated by the service provider, used to track the transaction. **Persist it** — it is what support traces with. | M |
| `timeStamp` | The time the request was sent | M |
| `statusDetail` | Detailed description explaining the status | M |

### `externalTrxId` rules

- Unique per logical charge, across all time. A UUID or ULID works; the documented example is a
  short numeric id, and mSpace publishes no length limit — do not invent one, and do not exceed
  whatever your own storage guarantees.
- **Persist before you send.** The correct order is: write a `PENDING` charge row → call the API
  → update the row from the response. If you crash in between you can reconcile; if you never
  wrote the row, the money is gone with no record.

### Documented status codes

`P1003`, `E1300`, `E1301`, `E1302`, `E1303`, `E1312`, `E1313`, `E1315`, `E1316`, `E1325`,
`E1329`, `E1330`, `E1337`, `E1342`, `E1343`, `E1371`, `E1601`, `E1603`, `E1604`, `E1607`,
`E1608`, `E1852`. See [09-status-codes.md](09-status-codes.md) for each one's meaning and class.

The ones specific to charging configuration are worth naming here:

| Code | Meaning | What to do |
|---|---|---|
| `E1329` | Charging amount too **high** for the NCS configuration | Fix the amount, or the configuration |
| `E1330` | Charging amount too **low** for the NCS configuration | Fix the amount, or the configuration |
| `E1371` | The application does not accept payments from the given payment instrument | Check the payment instruments enabled in CaaS configuration |
| `E1337` | Subscriber authentication failed | The subscriber did not confirm |
| `E1604` | Endpoint configuration missing | A URL the platform needs — such as the Charging Notification URL — is not configured |
| `E1607` | Unable to read application response | Your endpoint returned something the platform could not parse |
| `E1608` | SLA configuration error | Provisioning fix |
| `E1852` | Maximum number of OTP attempts reached | Stop; start a fresh charge only on a fresh user action |

## Step 3 — OTP Verification

```
POST /caas/otp/verify
Content-Type: application/json;charset=utf-8
```

Verifies the OTP the subscriber entered. **Upon a successful verification, the one-time charge is
deducted from the subscriber's mobile account.** This is the call that moves the money.

### Request

```json
{
  "applicationId": "APP_000999",
  "password": "…",
  "referenceNo": "8801442233146169943053700500040",
  "otp": "123456",
  "sourceAddress": "tel:94702725777"
}
```

| Parameter | Description | M/O |
|---|---|---|
| `applicationId` | Application ID from provisioning | **M** |
| `password` | The API key from application approval | **M** |
| `referenceNo` | **The `requestCorrelator` returned by OTP Generation**, used as the reference of the transaction | **M** |
| `otp` | The OTP the subscriber entered in your application | **M** |
| `sourceAddress` | The MSISDN that requested the OTP | **M** |

### Response

```json
{
  "statusCode": "S1000",
  "statusDescription": "Request was Successfully processed.",
  "status": true
}
```

| Parameter | Description | M/O |
|---|---|---|
| `statusCode` | `S1000` on success | M |
| `statusDescription` | Human-readable description of the outcome. **Note: `statusDescription`, not `statusDetail`.** | M |
| `status` | `true` if the OTP was valid and charging proceeded; `false` otherwise | M |

**This endpoint breaks the response envelope.** Everywhere else on the platform the human-readable
field is `statusDetail`; here it is `statusDescription`, and there is an extra boolean `status`. A
shared response parser that only knows `statusDetail` silently loses the message on the one call
that took someone's money. Handle it explicitly.

Documented codes: `S1000`, `E1312` (invalid request), `E1850` (invalid OTP), `E1852` (maximum
number of OTP attempts reached), `E1854` (could not find OTP), `E9999` (system error). The
endpoint's own enum additionally lists `E1855`, `E1856` and `E1337`.

## Step 4 — Charging Notification (inbound)

Configured during provisioning as the **Charging Notification URL** under CaaS configuration.
There is nothing to trigger: it is returned automatically as a callback to the initial charging
request once the transaction is completed within the system.

### Payload

```json
{
  "timeStamp": "2026-10-02T14:59:00+05:30",
  "version": "1.0",
  "externalTrxId": "256091234",
  "internalTrxId": "125100214570415",
  "referenceId": "12526",
  "currency": "LKR",
  "TotalAmount": "5.00",
  "paidAmount": "5.00",
  "balanceDue": "0.00",
  "statusCode": "S1000",
  "statusDetail": "Request was Successfully processed, Due amount fully paid."
}
```

| Field | Meaning |
|---|---|
| `externalTrxId` | Your transaction ID — **the reconciliation key** |
| `internalTrxId` | The unique identifier used to track the request at the developer application end |
| `referenceId` | The unique reference used to identify the transaction within the system |
| `TotalAmount` | Amount deducted from the subscriber as the one-time charge. **Capital `T`.** |
| `paidAmount` | The amount that is paid by the subscriber |
| `balanceDue` | The amount that is due, if any; otherwise `0` |
| `currency` | Only `LKR` is allowed |
| `timeStamp` / `version` | When it was sent, and the API version |
| `statusCode` / `statusDetail` | The final outcome |

Documented codes:

| Code | Meaning |
|---|---|
| `S1000` | Request was successfully processed, due amount fully paid |
| `E1404` | Charging request failed |
| `E1405` | Charging request timed out, no payments done |
| `E1852` | Maximum number of OTP attempts had reached |
| `E1854` | Could not find OTP |
| `E1855` | Invalid OTP reference number |
| `E1856` | OTP not found |
| `E1857` | Invalid reference number |

This is your **reconciliation channel**:

- Use it to resolve every charge your code left in `UNKNOWN` after a timeout.
- Match on `externalTrxId` — the key you generated and persisted before OTP generation.
- **Read `TotalAmount`, `paidAmount` and `balanceDue` together.** `S1000` says the due amount was
  fully paid; a non-zero `balanceDue` is what tells you it was not.
- Deduplicate on `externalTrxId` + `statusCode`. A repeat notification for an already-charged
  transaction must not double-count revenue.
- Respond `{"statusCode":"S1000","statusDetail":"Success"}` promptly, as with every callback. If
  you return something the platform cannot parse, the charging path reports `E1607`.

See [08-callbacks.md](08-callbacks.md).

## Charging state machine

```
PENDING ──P1003 (OTP sent)──► AWAITING_OTP     (persist requestCorrelator + internalTrxId)
   │
   ├─ any E-code on generation ─► FAILED       (nothing charged; investigate, do not blind-retry)
   └─ timeout / no answer ──────► UNKNOWN      (settle from the charging notification)

AWAITING_OTP
   ├─ verify S1000 + status true ─► CHARGED    (confirm on the charging notification)
   ├─ E1850 invalid OTP ──────────► AWAITING_OTP  (prompt again)
   ├─ E1852 attempts exhausted ───► FAILED     (start a new charge only on a fresh user action)
   └─ E1405 timed out, no payment ► FAILED

CHARGED confirmed by the charging notification: S1000 with balanceDue 0.00
```

## Balance query is not published

The mSpace OpenAPI document defines a `queryBalance` schema, but it publishes **no endpoint path
for it**. There is no documented way to call it, so this skill does not describe one and neither
should your code — do not invent a path. Handle an insufficient-balance outcome (`E1308`) on the
charge itself instead, which you have to do regardless, because a balance can change between any
check and the charge.

## Money-handling checklist for the charging path

- [ ] Amounts use a decimal type, never a binary float
- [ ] `externalTrxId` persisted **before** the OTP generation call
- [ ] Transaction row written before, updated after each of the three exchanges
- [ ] `P1003` treated as success on OTP generation
- [ ] `requestCorrelator` stored and passed as `referenceNo` to verification
- [ ] `internalTrxId` stored for support
- [ ] `statusDescription` (not `statusDetail`) read on the verification response
- [ ] `E1852` never retried automatically
- [ ] Timeouts resolved via the charging notification, not by re-charging
- [ ] `TotalAmount`, `paidAmount` and `balanceDue` all read before marking a charge complete
- [ ] Charging notification handler deduplicates on `externalTrxId` + `statusCode`
- [ ] Every charge traceable to a logged user action and consent record
- [ ] Amount and currency come from server-side config or a server-side price lookup — **never
      from client input**
